# Plan: The site's look, sign-in and a plain home screen

**Status:** written
**Outline:** `docs/outlines/coffee-tracker.md`, sections "Look and feel", "The first version" (Sign-in, Saved online, Home screen)
**Depends on:** nothing

## Goal

Give the site its calm coffee look and a front door. He opens the site, signs in once on
each device with his email and password, and from then on lands straight on a quiet coffee
home screen: today's date, one large copper **Brew** button and small links to Beans,
Recipes and History. None of those lead anywhere real yet; they show a short "not built
yet" page. Behind the scenes, the online database (Supabase, free plan) is set up and
locked so that only he can ever sign in, and signed-out visitors can't touch anything. No
coffee data is saved in this plan.

## Open questions for the owner

The plan is written using each recommendation. If he answers differently, the builder
adjusts the named step before starting.

1. **Whose name is the database account in?** Recommended: his own, created with his own
   GitHub login, so his data never depends on someone else's account. A helper can be
   invited to the project later if needed. Also: has the project already been created? If
   so, skip the "create project" part of hand batch A.
2. **Forgotten password.** Recommended: no "forgot password" link on the site for now. If
   he ever forgets it, he (or a helper with access) sets a new one in the Supabase
   dashboard in a minute. A reset-by-email link needs extra email and address settings for
   something a password manager makes very rare.
3. **What the bare site address opens.** Recommended: straight to the coffee home, while
   coffee is the only section. When section 2 arrives, he decides again (for example a
   small site menu). Changing it is one line.
4. **Does the coffee look cover the whole site?** Recommended: yes for now: cream,
   espresso and copper, the same fonts everywhere, so the site feels like one thing. The
   colours are named by job ("paper", "ink", "accent"), not by coffee, so a later section
   could change them without touching the coffee screens.

## What he sees

**First visit on a device (phone and desktop alike):** a cream page with the site name
in a serif font, an **Email** box, a **Password** box and a large copper **Sign in**
button. His phone's password manager can fill both boxes. If something goes wrong he sees
one plain sentence under the button, for example "That email or password isn't right." or
"Can't reach the internet. Check your connection and try again." Whatever he typed stays
in the boxes.

**After signing in, and every later visit:** the coffee home screen, with no sign-in step.

- At the top, a serif heading **Coffee** and today's date underneath in a quieter brown
  ("Wednesday 18 November").
- In the middle, one large copper **Brew** button: full width on a phone, about thumb
  height (64px), a comfortable fixed width on desktop.
- Below it, three small links in a row: **Beans · Recipes · History**.
- At the very bottom, a small muted **Sign out** link.
- Tapping Brew or any link fades to a short page: "This part isn't built yet." with a
  **Back** link. The phone's back button works too.

**Dark mode:** if the phone or computer is set to dark, the page is a near-black warm
brown with cream text and a slightly lighter copper. It switches by itself when the phone
does. The browser's top bar matches the page colour on phones that support it.

**Desktop:** the same screen as a calm centred column with lots of space around it. This
screen has nothing to put side by side; that comes with the history plan.

**If the site isn't connected to the database** (for example the settings were not added
to GitHub), it shows one calm sentence instead of breaking: "This site isn't connected to
its database yet." This is for him and the helper, not something he should normally see.

**Free-plan nap:** if nobody uses the site for a week, Supabase pauses the database and
sign-in fails with the "can't reach" message. Waking it is in the Notes, and the builder
tells him this in plain words when finishing.

## Data

- **His login** (email and password) lives in Supabase's built-in sign-in system, not in a
  table of ours. The password is stored scrambled; nobody, including Supabase staff,
  helpers or the AI, can read it. He keeps it in his password manager.
- **A "signed in" pass** (Supabase calls it a session) is kept in each browser's own
  storage so he stays signed in. It is not data: clearing the browser just means signing
  in again. It renews itself, so he stays signed in until he taps Sign out.
- **No coffee data and no tables** are created. Each later plan creates its own table and
  locks it in the same file (`.claude/skills/database-change/SKILL.md`).
- **One safety setting** (migration `001`) makes sure that any table created later is
  closed to signed-out visitors by default, even if a later plan forgot its lock.
- **New sign-ups are switched off**, so nobody else can make an account, even though the
  site's code and its public key are visible to anyone.
- **Keys:** the project URL and the **publishable** key are public by design and go in
  `.env` and in GitHub's Actions *variables*. The **secret** key and the database password
  are never used by this site and never go anywhere in the repo or chat.
- Nothing personal is committed. His email address does not go in any file.

## Steps

### 1. Pull and add the building blocks

Pull `main`. Add four packages: `@supabase/supabase-js` (talks to the database),
`react-router` (moving between screens with `#/` addresses), and the self-hosted fonts
`@fontsource-variable/source-serif-4` and `@fontsource-variable/inter`.

*Check:* `npm run check` still passes.

### 2. Settings reader and database connection

- `src/lib/config.ts`: a small pure function `readConfig(env)` that takes the two
  settings `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` and returns either both
  values or the list of names that are missing. Blank or whitespace-only counts as missing.
- `src/lib/supabase.ts`: if the config is complete, create one shared Supabase client
  with sessions kept in the browser and renewed automatically, and with
  `detectSessionInUrl: false` (see Notes). If not, export `null`, so screens can show the
  "isn't connected" sentence.
- `.env.example`: add both names with no values, each with a one-line comment saying it is
  public.

*Check:* `src/lib/config.test.ts` passes (see Testing).

### 3. Hand batch A: database project, his login, sign-ups off, keys

The builder gives him click-by-click steps (`.claude/skills/click-by-click/SKILL.md`),
checking Supabase's current docs for the exact labels first. Outline of the batch:

1. If the project doesn't exist yet, create it on the **Free** plan following steps 1 to 4
   of `walkthroughs/optional-database.md`. Never enter card details.
2. **Authentication → Users → Add user → Create new user**: his email and a new long
   password from his password manager, with **Auto Confirm User** ticked.
3. **Authentication → Sign In / Providers** (label may differ): turn off **Allow new users
   to sign up**, then **Save**.
4. From the project's **Connect** dialog or **Project Settings → API Keys**: copy the
   project URL into the `VITE_SUPABASE_URL=` line of `.env`, and the **publishable** key
   (starts `sb_publishable_`) into `VITE_SUPABASE_PUBLISHABLE_KEY=`. Not the secret key.

*Check:* the builder asks yes/no: "Does your publishable key start with
`sb_publishable_`?" Then `npm run dev` shows the sign-in screen, not the "isn't connected"
sentence (once step 6 exists; until then, the builder confirms it in step 6).

### 4. Migration 001 and hand batch B: closed to signed-out visitors by default

Write `supabase/migrations/001-lock-signed-out.sql`:

```sql
-- Signed-out visitors (Supabase's "anon" role) get no access to anything made later.
-- Each table still needs its own row level security policy in the file that creates it.
alter default privileges in schema public revoke all on tables from anon;
alter default privileges in schema public revoke all on sequences from anon;
alter default privileges in schema public revoke all on functions from anon;
```

Hand batch B: he opens **SQL Editor → New query**, pastes the file, clicks **Run**, and
should see "Success. No rows returned". Then he runs this check, which leaves nothing
behind:

```sql
begin;
create table wall_check (x int);
select has_table_privilege('anon', 'wall_check', 'select') as signed_out_can_read;
rollback;
```

*Check:* the result shows `signed_out_can_read` = `false`.

### 5. The look

- `src/index.css`: import the two fonts; set Tailwind's `font-serif` to Source Serif 4 and
  `font-sans` to Inter; body uses sans.
- Colours as CSS variables named by job, mapped into Tailwind (`@theme inline`) so screens
  write `bg-paper text-ink` and never need separate dark classes. Starting values (he
  eyeballs them; tweak freely):

  | Name | Job | Light | Dark |
  |------|-----|-------|------|
  | `paper` | page background | `#F5EFE6` | `#1A1411` |
  | `ink` | main text | `#2B1D14` | `#F1E7DA` |
  | `muted` | quiet text, links | `#7A6656` | `#A8978A` |
  | `line` | dividers, box borders | `#E2D6C6` | `#3A2E27` |
  | `accent` | Brew button, highlights only | `#A6603A` | `#C98352` |
  | `on-accent` | text on the accent | `#FFF8F0` | `#1A1411` |

  Dark values switch under `@media (prefers-color-scheme: dark)`. Text on the copper
  button is large and bold, and passes the contrast guideline for large text in both modes.
- A gentle 150ms fade-in for each screen, and a slight press response on buttons
  (`active:` slightly smaller and dimmer). Both turned off when the device asks for
  reduced motion.
- Numbers use the serif with even-width digits (`tabular-nums`) so they line up later.
- `index.html`: two `theme-color` tags (light and dark), `color-scheme` set to
  `light dark`. Title stays `<Daily Brad>`.

*Check:* `npm run dev`, switch the computer between light and dark: the page follows.

### 6. Sign-in

- `src/auth/signInMessage.ts`: a pure function turning Supabase's error into one plain
  sentence (wrong email or password; no connection or database asleep; too many tries;
  anything else: "Something went wrong signing in. Try again in a minute."). Tested.
- `src/auth/useSession.ts`: reads the saved session on start, listens for sign-in and
  sign-out, and reports "checking", "signed out" or "signed in".
- `src/auth/AuthGate.tsx`: while checking, shows the empty cream page (no flash of the
  sign-in screen); signed out shows `SignIn`; signed in shows the site. If the Supabase
  client is `null`, shows the "isn't connected" sentence.
- `src/auth/SignIn.tsx`: email box (`type="email"`, `autocomplete="username"`), password
  box (`autocomplete="current-password"`), large Sign in button that says "Signing in…"
  and can't be double-tapped while waiting. Inputs at least 16px text so phones don't
  zoom in. No sign-up link, no forgot-password link (open question 2).

Auth code lives in `src/auth/` and `src/lib/`, not in the coffee folder: sign-in belongs
to the whole site.

*Check:* `signInMessage.test.ts` passes; signing in with his real login on
`npm run dev` shows the home screen; a reload stays signed in.

### 7. Screens and addresses

- `src/App.tsx`: wraps everything in `AuthGate`, then a hash router (`HashRouter`):
  - `#/` goes to `#/coffee` (open question 3; one line to change later)
  - `#/coffee`: the coffee home
  - `#/coffee/brew`, `#/coffee/beans`, `#/coffee/recipes`, `#/coffee/history`: the
    "not built yet" page
  - any other address goes to `#/`
- `src/coffee/CoffeeHome.tsx`: heading, date, Brew button, three links, Sign out (which
  signs out and returns to the sign-in screen). Every tap target at least 48px tall.
- `src/components/NotBuiltYet.tsx`: shared by any section; the sentence and a Back link.
- The page column is centred with a maximum width of about 28rem and 16px side margins.

Remove the old "It works" page content.

*Check:* each link and the Brew button open the "not built yet" page; Back and the
browser's back button return home; typing `#/nonsense` lands on the home screen.

### 8. Prove the wall

Before calling it done, the builder runs, from the repo folder, a one-off command that
loads `.env` without displaying it and tries to create a new account with the public key:

```sh
node --env-file=.env -e "fetch(process.env.VITE_SUPABASE_URL+'/auth/v1/signup',{method:'POST',headers:{apikey:process.env.VITE_SUPABASE_PUBLISHABLE_KEY,'content-type':'application/json'},body:JSON.stringify({email:'wall-check@example.com',password:'Check-'+Date.now()})}).then(r=>r.text()).then(console.log)"
```

*Check:* the reply says sign-ups are not allowed (`signup_disabled`). If it instead
returns a new user, stop: sign-ups are still on. Go back to hand batch A step 3, and have
him delete the `wall-check@example.com` user in **Authentication → Users**.

Also by hand: a wrong password on the sign-in screen shows the plain sentence.

### 9. Publish

- `.github/workflows/deploy.yml`: give the `npm run check` step the two values from
  GitHub repository *variables*: `VITE_SUPABASE_URL: ${{ vars.VITE_SUPABASE_URL }}` and
  the same for the key. Variables, not secrets: these values are public and end up in the
  site's files anyway.
- Hand batch C: in the GitHub repo, **Settings → Secrets and variables → Actions →
  Variables** tab → **New repository variable**, once for each name, pasting the same
  values as in `.env`.
- `AGENTS.md`: update the Stack table's "Saving data" row to "Supabase (online database),
  locked per `.claude/skills/database-change/SKILL.md`", and add one Known-limits line:
  "Free Supabase projects pause after a week unused; restore from the dashboard."
- Run `npm run check`, commit (files staged by name), push `main`.

*Check:* the GitHub **Actions** tab shows the publish run green; the live site opens to
the sign-in screen on his phone.

## Testing

**Vitest (rules):**

- `src/lib/config.test.ts`
  - both settings present: returns both values
  - one missing: returns that name only; both missing: both names
  - blank or spaces-only counts as missing; surrounding spaces are trimmed
- `src/auth/signInMessage.test.ts`
  - Supabase's "invalid login credentials" error: the wrong email or password sentence
  - a network failure (fetch fails, or no status): the "can't reach the internet" sentence
  - a 429 "too many requests" error: "Too many tries. Wait a minute, then try again."
  - an unknown error: the general sentence, and never the raw technical text

**By hand (he tries it, phone first):**

1. On the phone, open the live site: sign-in screen, cream, serif name.
2. Sign in with the password manager. Home screen appears with today's date.
3. Close the browser completely, reopen the site: still signed in.
4. Tap Brew, Beans, Recipes, History: each shows "not built yet"; Back returns home.
5. Switch the phone to dark mode: the site turns dark brown with cream text.
6. Sign out, then type a wrong password: plain sentence, typed email still there.
7. Turn on airplane mode, try to sign in: the "can't reach the internet" sentence.
8. Sign in on the computer too: same home screen.

**Eyeball (looks aren't tested):** colours in light and dark, the two fonts, spacing and
calm, Brew button size with a thumb, link size, the fade between screens, the phone's top
bar colour, the desktop column.

## Notes

- **Supabase** is the database the repo's skills already name; the free plan is $0 and
  far larger than a coffee log needs. Never add card details. If Supabase ever asks for a
  paid plan, stop and ask him.
- **Waking a paused project:** sign in at supabase.com, open the project, click
  **Restore project** (label may differ), wait a few minutes. Data is kept. Daily use
  prevents the pause.
- **No tables yet, on purpose.** Each table is created and locked in the same file by the
  plan that first needs it (1.2 onward). An empty "settings" or "profile" table now would
  be built ahead of need.
- **Migration 001 is a backstop, not the lock.** Row level security policies on each table
  are the real wall. 001 only means a forgotten policy fails closed for signed-out
  visitors. It applies to tables made in the SQL Editor (owned by `postgres`), which is
  how every migration here is run. If it turns out to already be Supabase's default, it is
  harmless.
- **Why sign-ups off matters:** the publishable key is public. With sign-ups on, a
  stranger could make their own account; policies would keep them out of his rows, but
  they could still fill his free database. Off is simpler and safer.
- **`detectSessionInUrl: false`:** Supabase can read sign-in links from the address bar,
  which clashes with `#/` addresses. Password sign-in never uses such links. If
  reset-by-email is ever added, switch to Supabase's "PKCE" link style at that time.
- **Step 8 command:** `node --env-file` loads `.env` into the command without showing it,
  so the AI never reads `.env`; only Supabase's reply is printed. Later plans can prove
  their table locks the same way (a signed-out read returning `[]` or an error).
- **Router:** `react-router` with `HashRouter`, chosen over a hand-written address reader
  because later plans need addresses like `#/coffee/brew/…` and the back button handled
  properly, and every AI tool knows it well.
- **Fonts:** self-hosted through `@fontsource-variable` packages, chosen over a Google
  Fonts link: no outside request on every visit, works on a slow kitchen connection.
  Source Serif 4 has sturdy even-width digits that read well at arm's length; thin display
  serifs (such as Cormorant) were rejected as too faint with wet hands. Swapping a font is
  one line in `src/index.css`.
- **Colours by job, not by coffee name:** keeps the rule that nothing outside the coffee
  section assumes the site is only about coffee (open question 4).
- **Browser storage:** only the sign-in pass lives there, not his data, so the
  Export/Import rule for browser-saved screens doesn't apply to this plan. Backups of his
  coffee data come in `1.9-backups.md`.
- **"No connection" while saving** (outline) belongs to the plans that save data, from
  1.2 on. This plan only covers it for sign-in.
- **For later plans:**
  - Coffee screens go in `src/coffee/`; the addresses `#/coffee/brew`, `#/coffee/beans`,
    `#/coffee/recipes` and `#/coffee/history` are already wired to "not built yet":
    replace those routes, don't add duplicates.
  - Use the colour names (`paper`, `ink`, `muted`, `line`, `accent`, `on-accent`) and
    `font-serif` / `tabular-nums` for numbers; no raw colour codes in screens.
  - Use the shared client from `src/lib/supabase.ts`; never create a second one.
  - Migrations continue at `002-…`. Each table gets a `user_id uuid not null default
    auth.uid() references auth.users on delete cascade` column plus row level security
    and a policy in the same file.
