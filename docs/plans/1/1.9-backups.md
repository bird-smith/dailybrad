# Plan: Export and import backups

**Status:** written
**Outline:** `docs/outlines/coffee-tracker.md`, sections "The first version" (Backups)
**Depends on:** `1.7-ratings.md` (must be built first: rating columns on `brews`), and
through it 1.5 (`brews`), 1.3 (`recipes`), 1.2 (`methods`, `beans`, `setActiveBean`,
`dataMessage`, `ErrorLine`, `useLoad`) and 1.1. 1.6 and 1.8 change no stored data, so
they may come before or after.

## Goal

A safety copy he controls. On a quiet **Backup** screen he taps **Export backup** and his
phone or computer saves one file, `coffee-backup-2026-11-18.json`, holding every method,
bean (finished bags too), recipe and brew, ratings included. He keeps it somewhere off
the site: emailed to himself or in his cloud drive. If the database is ever lost (for
example a free project left paused too long) or he deletes something by mistake, he
chooses **Import a backup**, picks the file, sees exactly what will be added, and confirms.
Import puts back what is missing and never changes or deletes what is already on the site
(open question 1). If it stops partway, choosing the same file again finishes the job.

## Open questions for the owner

The plan is written using each recommendation. If he answers differently, the builder
adjusts the named step before starting, except where marked.

1. **Does import add what's missing, or replace everything?** Recommended: **add only.**
   Anything in the file that isn't on the site is put back; anything already on the site
   stays exactly as it is, and nothing is deleted. That covers both real uses: a lost
   database (everything is missing, so everything comes back) and a brew or bean deleted
   by mistake (it comes back with its date and rating). It can't undo an *edit*, and it
   is safe to run twice. The alternative, **replace**, first deletes every method, bean,
   recipe and brew on the site, then loads the file: an exact rewind, but anything logged
   since the backup is gone for good, and a wrong file wipes months of history. **This is
   destructive:** if he wants it, this plan goes back to be rewritten (a database function
   so the delete and reload happen in one go, plus a typed "Are you sure" step), not
   adjusted at build time. (Steps 2, 4.)
2. **Where is the Backup link?** Recommended: a small muted **Backup** link at the very
   bottom of the home screen, beside Sign out ("Backup · Sign out"): needed rarely, so it
   stays out of the way of the daily **Beans · Recipes · History** row. The alternative is
   a fourth link in that row, or a link at the bottom of History. (Step 4.)

## What he sees

**Home (changed from 1.1):** the bottom line reads **Backup · Sign out**, both small and
muted, each at least 48px tall to tap.

**Backup screen (`#/coffee/backup`):**

- Heading **Backup** and **Back**.
- One muted sentence: "A backup file is a copy of your methods, beans, recipes and brews.
  Keep it somewhere safe, away from this site: email it to yourself or put it in your
  cloud drive."
- A large copper **Export backup** button (the main action). "Exporting…" while it works
  (a second or two; longer with thousands of brews).
- Then the phone's or browser's usual download happens, and one muted line under the
  button: "Saved coffee-backup-2026-11-18.json: 4 methods, 9 beans, 12 recipes, 412
  brews. It's in your Downloads (on iPhone: the Files app, Downloads)."
- Below, with room above it, a quieter outlined **Import a backup** button. It opens the
  phone's or computer's file picker (only `.json` files offered where the device allows).

**After choosing a file:** the import area becomes a small bordered card:

- "Backup from Nov 18, 2026."
- What it adds, one plain sentence: "This adds 1 bean and 3 brews. Everything else in it
  is already here." Counts of zero are left out ("1 bean", "3 brews", singular and plural
  right). For an empty site: "This adds 4 methods, 9 beans, 12 recipes and 412 brews."
- Then, muted: "Nothing already on the site is changed or deleted."
- **Add them** (copper) and **Cancel**. Cancel returns to the two buttons.
- If nothing is missing: "Everything in this backup is already here." and **Done**, no
  Add button.

**While adding:** the card's buttons give way to a muted progress line ("Adding
methods…", "Adding beans…", "Adding recipes…", then "Adding brews… 500 of 1,412") and
"Keep this screen open until it says Done." **Export backup** can't be tapped meanwhile.

**Done:** "Done. Added 1 bean and 3 brews." They show straight away in Beans and History.
If no bag was active before and the backup's active bag came back, it is active again.

**When something goes wrong** (one plain sentence, never technical text, using the
shared `ErrorLine`):

- Not a backup (a photo, a random file, broken text): "This file isn't a coffee backup."
- A file too big to be a backup (over 20 MB): "This file is too big to be a coffee
  backup."
- Made by a newer version of the site: "This backup was made by a newer version of the
  site. Reload this page and try again."
- Damaged inside (a brew without a date, a link to a bean that isn't anywhere):
  "This backup file is damaged, so nothing was added." plus, smaller, which part
  ("brews, row 12"), for the helper.
- Export fails: "Couldn't export: can't reach the internet. Try again when you're
  connected." / "…you've been signed out. Sign in again in a new tab, then try again." /
  "Couldn't export. Try again in a minute." Nothing is downloaded.
- Import stops partway: the reason ("Couldn't finish: can't reach the internet."), then
  "Added so far: 4 methods, 9 beans, 12 recipes and 500 of 1,412 brews. Nothing was lost.
  Choose the same file again to add the rest."
- The database refuses part of the file: "The database refused part of this backup, so
  it stopped there. Choose the same file again; if this keeps happening, the file may
  have been changed by hand." plus "Added so far: …".

**Desktop:** the same screen in the centred column from 1.1.

**Phone and computer:** the data is online, so either device's backup holds everything.
The file itself lives only on the device that exported it, which is why it should go to
email or a cloud drive.

## Data

- **Nothing new in the database, no migration** (the next migration number stays `007`).
  Export reads the four tables; import adds rows to them through the same locks as every
  other screen ("own … only" from 002 to 004), so it can only ever add to his own data.
- **The backup file** (JSON, on his device, never on the site or in the repo):

  ```json
  {
    "kind": "coffee-backup",
    "version": 1,
    "exported_at": "2026-11-18T07:42:00.000Z",
    "methods": [ { "id": "…", "name": "V60", "created_at": "…" } ],
    "beans": [ … ], "recipes": [ … ], "brews": [ … ]
  }
  ```

  Each row holds the table's columns **except `user_id`**, ids included, so links between
  rows (a brew's bean, method and recipe) survive and a deleted row comes back as itself:

  - methods: `id, name, created_at`
  - beans: `id, name, roaster, roast_date, bag_grams, cost_cents, region, varietal, notes,
    finished, is_active, created_at`
  - recipes: `id, method_id, name, ratio, dose_grams, grinder, grind_size, temperature,
    bloom_seconds, total_seconds, steps, notes, created_at`
  - brews: `id, brewed_at, bean_id, method_id, recipe_id, recipe_name, dose_grams, ratio,
    grinder, grind_size, temperature, bloom_seconds, brew_seconds, steps, rating,
    taste_words, rating_note`

- **Not in the file:** water, days after roast, cups left, averages: all worked out from
  the rows, as on the site.
- **`user_id` is never sent;** the database fills in whoever is signed in.
- **Nothing in browser storage.** The file contains personal entries: it must never be
  committed. `.gitignore` gains `coffee-backup-*.json` as a safety net.

## Steps

### 1. Pull and confirm 1.7 is built

Pull `main`. Confirm `supabase/migrations/005-brew-ratings.sql` exists and has been run,
`src/coffee/types.ts` has `Method`, `Bean`, `Recipe`, `Brew` (with `rating`,
`taste_words`, `rating_note`), and `src/coffee/beansData.ts` has `setActiveBean`. If not,
stop: 1.7 comes first. If any later plan has added columns to these tables since, add
them to `BACKUP_COLUMNS` in step 2 (the type check there will insist).

*Check:* `npm run check` passes before any change.

### 2. Rules (pure functions, tested)

`src/coffee/backupFile.ts`:

- `BACKUP_KIND = 'coffee-backup'`, `BACKUP_VERSION = 1`, `MAX_BACKUP_BYTES = 20_000_000`.
- `BACKUP_COLUMNS`: the four column lists from Data, `as const`. A compile-time check
  makes `npm run check` fail if `Method`, `Bean`, `Recipe` or `Brew` has a field (other
  than `user_id`) missing from its list, so a later column can't silently stay out of
  backups.
- `Backup` type (hand-written): `kind`, `version`, `exported_at`, and the four arrays of
  rows (each table's type without `user_id`).
- `makeBackup(rows, now)`: the `Backup` object, keeping only the listed columns.
- `backupFileName(now)`: `coffee-backup-2026-11-18.json` from the **local** date.
- `readBackup(text)`: `JSON.parse` in a try; checks `kind`, then `version` (a whole
  number from 1 to `BACKUP_VERSION`; higher is the "newer version" sentence), then each
  table is a list of objects with an id shaped like a uuid, no id twice in one table, and
  the fields each insert can't do without, with the right kind of value: method `name`;
  bean `name`; recipe `method_id`, `name`, `ratio`, `dose_grams`, `steps` (a list);
  brew `brewed_at` (a real date), `bean_id`, `method_id`, `recipe_name`, `dose_grams`,
  `ratio`, `steps` (a list), `taste_words` (a list, when present). Unknown fields are
  dropped; known fields missing from an older file are simply not sent, so the
  database's defaults apply. Returns the clean `Backup` or `{ problem, where }` with the
  sentences from "What he sees". It does not re-check every length and range: the
  database does that, and an exported file already passed it.

`src/coffee/backupImport.ts`:

- `planImport(file, current)`: `current` is what's on the site now (methods' ids and
  names; recipes' ids, methods and names; beans' ids and which is active; brews' ids).
  Decides, table by table in link order:
  - **methods:** id already on the site: kept. Else the same name ignoring capitals
    already on the site: treated as that method (the database allows no two V60s), and
    everything in the file pointing at it is pointed at the site's one instead. Else
    added.
  - **beans:** id on the site: kept. Else added, **always with `is_active` false** (the
    database allows only one active bag; see the last rule).
  - **recipes:** method looked up through the methods above; not in the file or on the
    site: damaged. Id on the site: kept. Else the same name ignoring capitals in that
    method, on the site or earlier in this import: treated as that recipe. Else added,
    with the looked-up method.
  - **brews:** id on the site: kept. Bean in neither the file nor the site: damaged.
    Method looked up as for recipes. Recipe looked up likewise; when it is nowhere, the
    link is left empty and `recipe_name` keeps the name (exactly what deleting a recipe
    does in 1.5). Else added.
  - **active bag:** when no bag is active on the site now and the file's active,
    unfinished bag is one being added, its id is returned to be made active afterwards.
    A bag already on the site is never touched.
  - Returns `{ add: { methods, beans, recipes, brews }, keptCount, activeBeanId }` or the
    damaged sentence with where.
- `countsSentence(counts)`: "4 methods, 9 beans, 12 recipes and 412 brews", "1 bean and
  3 brews", zeros left out, `en-US` thousands commas ("1,412").
- `importPreview(plan)`: "This adds … Everything else in it is already here." (second
  sentence only when something was kept), or "Everything in this backup is already here."
- `progressLine(table, done, total)`: "Adding brews… 500 of 1,412".
- `inBatches(rows, size)`: splits a list into lists of at most `size` (500 is used).

`src/lib/dataMessage.ts` (shared, tested): add the actions `export` and `import` with the
sentences in "What he sees"; for `import`, codes `23502`, `23503`, `23505` and `23514`
(the database refusing a row) give the "refused part of this backup" sentence.

*Check:* `npx vitest run src/coffee/backupFile.test.ts src/coffee/backupImport.test.ts
src/lib/dataMessage.test.ts` passes.

### 3. Talking to the database

`src/coffee/backupData.ts`, using only the shared client:

- `readAllPages(fetchPage)`: asks for rows 0–999, then 1000–1999, and so on, **until a
  page comes back empty**, and returns them all in order. Stopping on an empty page (not
  on a short one) stays correct even if the project's row limit is set below 1000. Takes
  the page function as an argument so Vitest can test it with a fake.
- `exportAll()`: the four tables, each with its `BACKUP_COLUMNS` (never `*`, so `user_id`
  stays out), ordered by `created_at, id` (brews by `brewed_at, id`) so pages don't shift,
  through `readAllPages`. Returns the rows or the first error.
- `readCurrent()`: the same paging, but only `id, name` of methods, `id, method_id, name`
  of recipes, `id, is_active` of beans and `id` of brews: what `planImport` needs.
- `addRows(table, rows, onProgress)`: plain `insert` in batches of 500 (one request each,
  so each batch goes in whole or not at all), calling `onProgress(done)` after each.
  Stops at the first error and returns it with how many went in. Plain insert, not
  "insert or skip": a clash is reported instead of silently dropping a row.
- Then, if `activeBeanId` is set, `setActiveBean` from `beansData.ts`.
- Never sends `user_id`. Sends `id`, `created_at` and `brewed_at` from the file, so dates
  and order are kept.

*Check:* `npx vitest run src/coffee/backupData.test.ts` passes, then `npm run check`.

### 4. The Backup screen and its link

- `src/coffee/BackupScreen.tsx` at `#/coffee/backup` (route added in `src/App.tsx`), as in
  "What he sees". Export: `exportAll` → `makeBackup` → `JSON.stringify(backup, null, 2)`
  → a file download (a `Blob`, a temporary link with `download` set to

  preview card; **Add them** runs `addRows` for methods, beans, recipes, brews in that
  order, updating the progress line, then `setActiveBean` if needed. Choosing the same
  file twice in a row must work (clear the input's value after each choice).
- Busy states as on every screen: buttons can't be double-tapped; Export is disabled
  during an import and the other way round.
- `src/coffee/CoffeeHome.tsx`: the bottom line becomes **Backup · Sign out** (open
  question 2).
- `.gitignore`: add `coffee-backup-*.json`.

*Check:* on `npm run dev`, Export downloads a file that opens as readable text with the
four lists; importing it straight back says "Everything in this backup is already here."

## Notes

- **Add-only import from the site, no database function.** Because it only adds what's
  missing, running it again after a dropped connection simply finishes the job, so it
  doesn't need to happen "all in one go". Rejected: a `restore_backup` database function
  taking the whole file (a migration, file checking in SQL that Vitest can't test, and
  only worth it for a replace, which is open question 1).
- **Plain insert of only the missing rows**, rejected: "insert or skip on clash"
  (`upsert` ignoring duplicates). Skipping hides problems: a row clashing with something
  the site can't see would vanish silently while the summary claimed it was added.
- **Ids kept from the file**, rejected: fresh ids on import (every import would duplicate
  everything, and links between rows would need rebuilding).
- **Same-name method or recipe is treated as the same one**, rejected: refusing the
  import. The database allows no two V60s, so the only other choice is stopping, and
  "V60 deleted and added again" is exactly when a backup is needed.
- **New bags arrive inactive, then the active one is set with `set_active_bean`**, because
  the database allows at most one active bag; inserting the file's flag as-is would clash
  with the bag active now.
- **JSON, one file**, rejected: CSV (four files or one awkward sheet; steps, pours and
  taste words are lists that don't fit cells) and a spreadsheet file (a library for no
  gain). JSON keeps every value exactly as the database holds it.
- **Paging until an empty page**, rejected: stopping at the first page under 1000
  (silently cuts the backup short if the project's limit is ever lowered) and one
  request with no paging (Supabase returns at most 1000 rows).
- **Batches of 500 rows** keep each request well under size limits while 1,000 brews take
  two requests.
- **20 MB limit** stops a wrong file (a video) from freezing the phone; a real backup of
  several thousand brews is a few MB.
- **Coffee only**: the backup lives under `#/coffee/backup` and the file says
  `"kind": "coffee-backup"`. When section 2 has data of its own, it gets its own backup
  (or a site-wide backup page can gather the sections then). Rejected now: a site-wide
  file that would have to assume coffee is all there is.
- **Download, not the phone's share sheet**, rejected for now: share sheet support for
  files varies between phones and browsers; a download works everywhere. Could be added
  later if saving to the cloud drive from the phone proves fiddly.
- **Restoring into a brand-new database project:** run migrations 001 onward in order
  (1.1 to the latest plan), sign in, then import. Everything is missing, so everything
  comes back with its own ids and dates.
- **Rejected for now:** automatic or scheduled backups (stub: not this plan), a "last
  backed up 3 weeks ago" reminder (would need browser storage or a new column; he can
  ask for it), choosing which tables to export.
- **For later plans:** any plan that adds a column or table to coffee data adds it to
  `BACKUP_COLUMNS` (the type check enforces this for the four existing types) and to
  `readBackup`'s required fields if it can't be empty. A new required field means
  `BACKUP_VERSION` 2, with `readBackup` still accepting version-1 files. A new table needs
  its own list, its place in the import order, and `planImport` rules. `1.10-bean-supply`
  stores nothing new, so it needs no change here.
